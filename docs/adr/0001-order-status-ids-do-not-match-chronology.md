# ADR-0001: Значения order_status из API не совпадают с хронологией переходов

Контекст: API бэкенда «Умной логистики» кодирует жизненный цикл заявки полем `order_status` со значениями 1–5, которые закреплены и не подлежат изменению на стороне приложения. Хронологический путь водителя — **1 (Новая) → 2 (В работе) → 5 (Погружен) → 4 (Завершена)**, а статус **3 (Отказ)** — терминальный и достижим из 1, 2 или 5 отменой. Таким образом, численный порядок ID (1,2,3,4,5) не совпадает с хронологией: 5 предшествует 4, а 3 ортогонально «Отказу» и не стоит между 2 и 4.

Решение: доменная модель принимает коды статусов из API как данность — `OrderStatus` остаётся `enum` с `id` из API (1–5), а хронологические правила (однонаправленность, обязательность прохождения 5, права акторов) описаны исключительно в `CONTEXT.md` как инварианты, без введения отдельного внутреннего enum с «правильной» нумерацией.

Рассмотренная альтернатива: ввести внутренний enum (например, `proposed → accepted → loaded → completed` + отдельный `rejected`) и маппить его на API-коды в репозитории. Отвергнута как дублирование сущностей ради косметики: различий в поведении между внутренним и API-представлением нет, а второй источник правды о переходах создал бы риск рассинхрона с бэкендом.

Последствие: логика, зависящая от порядка (сравнения «статус позднее/раньше», валидация переходов, фильтрация «активных»), **не должна** опираться на численное сравнение `order_status`. Активность по линии 2/5 выражается явным методом `OrderStatus.isInProgressActive`; любые новые сравнительные проверки обязаны реализовываться явно по бизнес-правилу, а не через операторы `<`/`>`.
