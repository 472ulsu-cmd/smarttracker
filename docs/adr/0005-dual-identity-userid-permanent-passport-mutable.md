# ADR-0005: Дуальная модель идентичности — User.id перманентен, Паспорт сменяем

Контекст: в системе сосуществуют два способа идентификации водителя. Платформа и приложение «Умный Водитель» идентифицируют водителя по `User.id`. ТК в своём справочнике идентифицирует водителя по Паспорту. Водитель может сменить паспорт (замена по возрасту, утеря) — это штатный сценарий, поддержанный `POST /user` (поле `login`).

Решение: `User.id` — **перманентный ключ идентичности**: не меняется при смене паспорта, к нему привязаны заявки (как активные, так и висящие), история, аватар, пароль. Смена паспорта — обновление сменяемого атрибута `login` в той же учётной записи. Для **ТК**, напротив, паспорт — идентификатор в её справочнике: при смене паспорта старая связь ТК↔водитель по старому номеру рвётся, и ТК должна заново добавить водителя в справочник по новому паспорту. Тонкое различие: ТК назначает заявку «по паспорту», но платформа резолвит паспорт в `User.id`, и именно к `User.id` заявка привязывается фактически (см. ADR-0003).

Рассмотренная альтернатива: единый перманентный идентификатор на всех уровнях — например, сделать паспорт неизменяемым (нельзя редактировать `login`), либо завести сквозной идентификатор, который ТК тоже использует вместо паспорта. Отвергнута: паспорт в РФ сменяем по закону (20/45 лет, утеря), запрет на редактирование сломал бы реальный жизненный цикл водителя; а навязывание ТК внутреннего `User.id` вместо понятного паспорта нарушило бы UX диспетчера и контракт платформы со справочником ТК.

Последствие: модель идентичности намеренно **дуальна** — это не баг, а отражение двух разных контекстов (платформа vs справочник ТК). Смена паспорта сохраняет непрерывность учётной записи для водителя и платформы, но **разрывает** связь с ТК до явного повторного добавления. Будущему инженеру нельзя «починить» это расхождение, унифицировав идентификатор, — потеряется либо реальный жизненный цикл паспорта, либо контракт со справочником ТК.
