# ADR-0002: Сервер — единственный источник истины о Статусе заявки

> **Status: proposed (целевое состояние).** Решение зафиксировано как целевой контракт по итогам доменного моделирования. Текущий код ему **не соответствует** — см. раздел «Состояние реализации» ниже. До устранения разрывов ADR остаётся в статусе proposed.

Контекст: водитель может инициировать смену статуса заявки, находясь вне зоны сети; действие попадает в очередь `pending_actions` и отправляется позже. При этом правила перехода (`CONTEXT.md`, «Статус заявки») строгие и однонаправленные, а диспетчер Платформы может параллельно отменить ту же заявку (2→3 или 1→3). Возникает гонка: локально водитель видит, например, статус 5 «Погружен», а серверная истина — 3 «Отказ».

Решение: единственным источником истины о Статусе заявки признаётся **ответ сервера**. Отложенный `statusChange` трактуется как best-effort уведомление о намерении, а не как гарантия применения: если на момент доставки целевой переход недостижим (например, заявка уже в терминальном «Отказе» 3), сервер его отвергает, а приложение **откатывает локальный статус до серверной истины** при следующей синхронизации. Очередь не «доводит переход любой ценой».

Рассмотренная альтернатива: трактовать очередь как гарантированную доставку и применять отложенный переход с приоритетом над сервером (в духе CRDT/last-write-wins на стороне клиента). Отвергнута: она нарушает зафиксированные правила переходов (возврат из 3 невозможен), ломает право диспетчера на отмену и расходится с тем, что статус — наблюдаемое свойство заявки, owned платформой.

Последствие: UX-решение «нажал кнопку → увидел новый статус» — это **локальный оптимизм**, а не обязательство; приложение должно быть готово откатить показанный статус при рассинхроне. Отсюда же следует, что `PendingAction`/`statusChange` концептуально ближе к best-effort телеметрии, чем к транзакции, и не является доменной сущностью.

## Состояние реализации (на момент аудита)

**Online-happy-path:** свойство «сервер = истина» соблюдается. `OrderDetailViewModel.changeStatus` (`lib/ui/features/orders/view_models/order_detail_view_model.dart:86-116`) не делает optimistic-write локального статуса; после успешного HTTP выполняется `fetchOrderDetail` и экран перерисовывается серверной истиной.

**Offline-then-rollback контракт ADR-0002 — НЕ реализован.** Подлежит устранению:

1. **Offline-смена статуса не очередизуется.** При `NetworkException` намерение выбрасывается (показ ошибки), а не кладётся в `pending_actions` (`order_detail_view_model.dart:103-111`). Контраст: `PhotoViewModel` корректно очередизует `photoUpload` при отсутствии сети (`lib/ui/features/photos/view_models/photo_view_model.dart:126-139`) — аналогичный обработчик для статусов отсутствует.
2. **Потребитель `statusChange` мёртв.** Ветка `case PendingActionType.statusChange` в `sync_service.dart:70-75` не имеет producer'а в проде (только в `test/`).
3. **Rollback-а нет.** При провале повторной отправки — `debugPrint` + `markFailedAttempt` (`sync_service.dart:50-53`), без `fetchOrderDetail`/`fetchActiveOrders` для реконсиляции с сервером.
4. **`failed`-записи молча расходятся.** `readPending` фильтрует по `status='pending'` (`pending_action_store.dart:65-67`), `failed`-строки не читаются и не показываются пользователю — локальный статус может бесконечно расходиться с сервером.
5. **Нет триггера реконсиляции.** Зависимости `connectivity_plus` и листенера восстановления сети нет; обновление локального состояния — только ручной pull-to-refresh или `OrdersRefreshBus` (стреляет лишь при *успешной* онлайн-смене или пуше).

**Долг:** привести код к целевому контракту — очередизация `statusChange` при offline, реконсиляция локального статуса с сервером при отказе/восстановлении сети, явное информирование пользователя о невосстановимых `failed`. До этого момента фактическое поведение приложения = «online-only для смены статуса; offline-смена отвергается с ошибкой».
